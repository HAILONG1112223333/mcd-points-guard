# 🍟 麦麦积分止损官（mcd-points-guard）

> **你的麦当劳积分，一半已经蒸发了。**
>
> 这是一个基于麦当劳中国官方 MCP 的积分体检工具：算出你有多少积分正在悄悄过期、
> 每 100 积分到底值多少钱、以及怎样把积分刚好花完不浪费。

**用真实账户跑出来的结果（2026-10-23 实测）：**

```
累计积分 2167.9   已过期 1111.9   →   51.3% 的积分蒸发了
积分商城 23 个商品   16 个已过期   →   70% 根本换不了
同样 1025 积分：会换 ¥53.5  vs  不会换 ¥21.9   →   差 2.44 倍
```

---

## 它解决什么问题

麦当劳的积分有有效期，过期即清零。但会员很难知道三件事：

1. **我有多少分快过期了？** —— 官方只给一个数字，不告诉你这等于损失多少钱
2. **换哪个划算？** —— 商城列表按品类排列，不按性价比，50 分的小食和 800 分的套餐看起来差不多
3. **积分怎么刚好花完？** —— 剩几百分不上不下的，最后还是烂在手里

本工具用官方接口的真实数据回答这三个问题。**价格与积分只认接口返回值，绝不推算。**

### 接实时数据（可选）

需要麦当劳 MCP Token：[open.mcd.cn/mcp](https://open.mcd.cn/mcp) 手机号登录 → 控制台 → 激活 → 复制，免费。

在任意支持 MCP 的客户端（WorkBuddy / Cherry Studio / Cursor / Trae / VSCode）里配置：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn/mcp-servers/mcd-mcp",
      "headers": { "Authorization": "Bearer ${MCD_MCP_TOKEN}" }
    }
  }
}
```

⚠️ **Token 绑你的会员账号，绝不提交到公开仓库。** 用环境变量注入。

## 核心发现

### ① 积分汇率在不同商品间差 5 倍

汇率 = 兑换价 ÷ 所需积分 × 100，衡量「每 100 积分能撬动多少元消费」。

| 商品 | 积分 | 兑换价 | 汇率 |
|---|---:|---:|---:|
| 🔥 6.9元可乐麦炫酷 | 50 | ¥6.9 | **13.80** 元/100分 |
| 🔥 6.9元香芋派/菠萝派任选 | 50 | ¥6.9 | **13.80** 元/100分 |
| 10.9元指定小食任选 | 100 | ¥10.9 | 10.90 |
| 10.9元指定小食任选 | **200** | ¥10.9 | 5.45 |
| 17.9元板烧可乐组合 | 500 | ¥17.9 | 3.58 |
| 💀 21.9元巨无霸可乐组合 | 800 | ¥21.9 | **2.74** |

**规律：小面额兑换远优于大面额。** 50 分的商品汇率是 800 分的 5 倍。
直觉上「攒着换大的」恰恰是最亏的做法。

**还有个坑**：列表里有两个同名商品「10.9元指定小食任选」，一个 100 分一个 200 分。
不比对积分的话完全看不出区别，等于白多花一倍积分。

### ② 积分商城 70% 的商品换不了

接口返回的 23 个积分商品中，16 个的 `downTime` 早于当前时间。
列表不会自动过滤，用户看到「可以兑换」，实际点进去才发现已过期。
本工具按有效期过滤，只展示真正能换的。

### ③ 凑单比全押更值

用子集和 DP 在积分预算内最大化总价值：

```
会换：  50+50+100+200+500 = 900 分  →  ¥53.5（剩 125 分）
不会换：全押巨无霸组合 800 分        →  ¥21.9（剩 225 分不够换任何东西）
                                        差 2.44 倍
```

## 算法

**分工原则：取数交给 MCP，算术交给 Python。**

大模型做加减乘除和多约束枚举并不可靠；把枚举放进代码，结果才可复现、可验证。

```
now-time-info         当前时间（判断商品是否过期）
query-my-account      可用 / 累计 / 已过期 / 本月将过期积分
query-nearby-stores   定位门店（价格随门店变化）
mall-points-products  积分商城商品（名称 / 所需积分 / 上下架时间）
query-meals           门店菜单（用于「净省」口径的价格锚定）
        ↓
  filter_redeemable()   过滤 point>0 且 upTime ≤ now ≤ downTime
  compute_rates()       汇率 = pay / point × 100
  optimize()            子集和 DP，预算内最大化总价值
```

**两个口径，都标注清楚**：

- **汇率**（主指标）：`兑换价 ÷ 积分 × 100`，100% 可从接口数据算出，可复现
- **净省**（参考列）：`门店原价 − 兑换价`，仅在能匹配到菜单原价时给出；
  匹配不到**留空不猜**

**估值用中位数汇率**而非均值——汇率分布长尾严重，均值会被极值拉偏。

## 安全边界

- **只读优先**：本工具默认只读。`mall-create-order` 会真实扣减积分，
  仅在用户明确说「兑换」且二次确认后才调用
- **不猜价格**：匹配不到就标「未知」，绝不用估算值填充
- **凑单反而更贵就说别凑**：不为凑满而推荐
- **Token 只在环境变量里**：仓库内所有配置均为占位符
