# 🍟 麦麦积分止损官（mcd-points-guard）

> **你的麦当劳积分，一半已经蒸发了。**
>
> 基于麦当劳中国官方 MCP 的积分体检工具：算出你有多少积分正在悄悄过期、
> 每 100 积分**真金白银省多少钱**、以及怎样把积分刚好花完不浪费。

**用真实账户跑出来的结果（2026-10-23 实测）：**

| | |
|---|---|
| 累计积分 **2167.9** → 已过期 **1111.9** | **51.3% 的积分蒸发了** |
| 积分商城 23 个商品 → 16 个已过期 | **70% 根本换不了**，真正能换的只有 7 个 |
| 同样 1025 积分 | 背包凑单省 **¥31.20** vs 全押最大额省 **¥14.10**，差 **2.21 倍** |

---

## 它解决什么问题

麦当劳积分有有效期，过期即清零。但会员很难知道三件事：

1. **我有多少分快过期了？** —— 官方只给一个数字，不告诉你这等于损失多少钱
2. **换哪个划算？** —— 商城按品类排列不按性价比；更要命的是，「21.9元巨无霸组合」里的 21.9 **不是你换到的价值，是你还要掏的现金**
3. **积分怎么刚好花完？** —— 剩几百分不上不下，最后还是烂在手里

本工具用官方接口的真实数据回答这三个问题。**价格与积分只认接口返回值，绝不推算。**

## 核心发现

### ① 商品名里的金额是「付现」，不是「到手价值」

这是本项目第一版踩过的坑，也是最容易误导人的地方：

```
「21.9元巨无霸可乐组合」  800 分
  门店原价 ¥36.0（巨无霸 26.5 + 可乐 9.5）
  兑换时你还要付 ¥21.9
  ⇒ 真正省下的是 36.0 − 21.9 = ¥14.1
```

第一版用 `pay ÷ point` 当「汇率」，得到 2.74 并把它标成「💀血亏」。**那是付现率——每 100 积分要掏多少现金，不是收益。** 方向是反的。

本项目现在的口径：

```
净省   = 门店原价 − 兑换付现
净省率 = 净省 ÷ 所需积分 × 100     ← 每 100 积分真金白银省多少
```

### ② 净省榜（原价取自门店菜单实价，非估算）

| 商品 | 积分 | 付现 | 净省 | 净省率 |
|---|---:|---:|---:|---:|
| 🔥 6.9元可乐麦炫酷 | 50 | ¥6.9 | ¥6.1 | **12.20** 元/100分 |
| 6.9元香芋派/菠萝派任选 | 50 | ¥6.9 | ¥1.6 | 3.20 |
| 16.9元麦辣可乐组合 | 500 | ¥16.9 | ¥15.6 | 3.12 |
| 17.9元板烧可乐组合 | 500 | ¥17.9 | ¥15.6 | 3.12 |
| 21.9元巨无霸可乐组合 | 800 | ¥21.9 | ¥14.1 | 1.76 |

**小面额券的单分效率更高**，但**大面额券的绝对净省更大**——两者不是一回事，这正是需要算而不是凭感觉的原因。

### ③ 按性价比一个个买，反而少省钱

这是背包问题的经典反直觉之处：

| 策略 | 花掉 | 净省 |
|---|---:|---:|
| **背包 DP 凑单**（麦辣 500 + 板烧 500） | 1000 分 | **¥31.20** |
| 按净省率贪心买（麦炫酷+派+麦辣） | 600 分 | ¥23.30 |
| 全押最大额（巨无霸 800） | 800 分 | ¥14.10 |

贪心策略把预算花在高净省率的小额券上，结果**还剩 425 分没处花**，总共反而少省 ¥7.9。
**凑单比贪心多省 1.34 倍，比全押多省 2.21 倍。**

### ④ 积分商城 70% 的商品换不了

接口返回的 23 个积分商品中，16 个的 `downTime` 早于当前时间。
列表不会自动过滤，用户看到「可以兑换」，点进去才发现已过期。
本工具按有效期 + `status` 过滤，只算真正能换的。

### ⑤ 已过期积分不是资产

1111.9 分按净省率折算**本可值 ¥34.69**，但它已经归零——**当前可变现 ¥0**。
把它们按汇率估成「还值 ¥60」是自欺欺人，本工具会把「本可值」和「可变现」分开写。

## 算法

**分工原则：取数交给 MCP，算术交给 Python。**

大模型做加减乘除和多约束枚举并不可靠；把枚举放进代码，结果才可复现、可验证。

```
now-time-info         当前时间（判断商品是否过期）
query-my-account      可用 / 累计 / 已过期 / 本月将过期积分
query-nearby-stores   定位门店（价格随门店变化）
mall-points-products  积分商城商品（名称 / 所需积分 / 上下架时间 / status）
query-meals           门店菜单（净省口径的价格锚定）
        ↓
  filter_redeemable()   point>0 且 upTime ≤ now ≤ downTime 且 status 在售
  compute_rates()       net_rate = (原价 − 付现) / point × 100
  optimize()            0/1 背包 DP，预算内最大化 Σ 净省
```

**三个口径，都标注清楚**：

| 口径 | 公式 | 用途 |
|---|---|---|
| **净省率**（主指标） | `(原价 − 付现) / 积分 × 100` | 排序、估值、优化目标 |
| 货值率 | `付现 / 积分 × 100` | 原价匹配不到时的下限参考，**不参与推荐** |
| 净省 | `原价 − 付现` | 绝对值，回答「到底省了几块钱」 |

**估值用中位数净省率**而非均值——分布长尾严重，均值会被极值拉偏。

**约束**：每种券限兑 1 次（积分商城常见规则）；同 `spuId` 去重；
平局优先多消耗积分（目标是止损，不是攒分）。

## 已知缺口（不掩饰）

- **「10.9元指定小食任选」两张券（100/200 分）未能参与优化** —— 菜单里匹配不到「指定小食」的原价，接口也没给。按 ¥14.5 推算的话，100 分档净省率可达 **3.60**，可能优于板烧/麦辣。但那是推测不是数据，本项目选择**留空不猜**，只在报告里单列「货值参考」并提示。
- **人工补价入口**：若你知道某张券的实际原价，填进 `data/combo_map.json` 即可纳入计算：

  ```json
  {
    "_readme": "唯一允许人工输入数字的地方，其余全部来自接口",
    "bySpuId": { "17076": 14.5 },
    "byName":  { "10.9元指定小食任选": 14.5 }
  }
  ```

  实测补 `17076: 14.5` 后，该券会从「货值参考」升到净省榜第 2 名（3.60 > 3.12），
  但**最优方案仍是 500+500 的 ¥31.20** —— 100 分装不进剩下的 25 分预算。
  补价会改变榜单排名，不会凭空抬高结论。补价的券在报告里打 `〔原价人工补〕` 标签，可追溯。
- 价格随门店变化，每次会话需先确定门店上下文，不能跨店套用。

## 安全边界

- **只读优先**：默认只读。`mall-create-order` 会真实扣减积分，
  仅在用户明确说「兑换」且二次确认后才调用
- **不猜价格**：匹配不到就标「未知」，绝不估算填充
- **凑单反而更贵就说别凑**：不为凑满而推荐
- **Token 只在环境变量里**：仓库内所有配置均为占位符
